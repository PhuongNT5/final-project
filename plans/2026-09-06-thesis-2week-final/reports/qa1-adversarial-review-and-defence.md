## C. Defence Q&A

**Q1: "You didn't beat the paper — what's the contribution?"**
A: We don't claim to beat it, and can prove no system can be shown to beat it at n=64 (McNemar best-case p=0.50 even at 64/64, `t1-objectives-audit.md` §3b, independently re-derived here in scipy). The contribution is statistical-tie-at-scale (k-fold 84.0% macro ±3pp vs their single 64-clip point, no CI) + measured edge deployment + safety-oriented evaluation axes (calibration, FNR, cost-sensitive scoring, cross-camera) the paper never attempted. Evidence: `sweep_results/relation_tokens/kfold_oof_softmax_yolo26app_.pt` (417/516=80.8%, macro 84.0%, independently recomputed).

**Q2: "Your accuracy is lower than a 2024 published result."**
A: True at face value (54/64=84.4% vs 57/64=89.06% no-bbox baseline on top-1), but the gap is not statistically significant (z=−0.78, p=0.435, independently recomputed) and our result is on **macro** recall (88.4%) which *exceeds* their no-bbox macro (85.78%) — the paper's reported macro advantage direction actually favors us on the metric that matters most for a 4-class safety task with imbalanced classes. We report both numbers, do not cherry-pick.

**Q3: "Is this novel, or just engineering composition?"**
A: README already concedes this explicitly ("YOLO-Transformer engineering composition... not a new architectural mechanism," README.md L3). Novel contributions are: (a) fair paper-scale reproduction of their pipeline including the frame-reduction gate, (b) rigorous statistical evaluation absent from the original (bootstrap CI, Nadeau-Bengio, exact McNemar), (c) cross-camera generalization protocol they never ran, (d) measured edge-deployment numbers. We do not claim architectural novelty.

**Q4: "N=64 test set — statistically meaningful?"**
A: No, by construction — and we say so. Minimum detectable difference at n=64 is ~15-20pp (bootstrap CI width, `t1-objectives-audit.md` §3c); resolving-power analysis (r5, Fisher-z on val/test correlation) independently confirms this benchmark cannot resolve model differences below ~15pp true gap. This is *why* we run k-fold on 516 pooled clips (±3pp CI) as our statistical-reliability evidence instead of leaning on the 64-clip point estimate alone.

**Q5: "Leave-camera-out with only 2 cameras / 7-8 views — valid protocol?"** (attack hardest)
A: Partially conceded. Two real, found problems: (1) the original view-grouping was **circular** (KMeans clustered on the same classifier features used downstream) — fixed via classifier-independent static-background clustering (`tools/build_scene_grouping.py`, `phase0-D1-repaired-lco-grouping.md`); the fix barely moved the model number (78.6%→80.1%/82.0% depending on run), so the signal survives the repair. (2) The **baseline** used to claim a margin was broken — comparing a per-view-majority baseline (k-fold) against a constant-global-majority baseline (LCO) across different protocols, an apples-to-oranges comparison (`brief.md` S2, independently code-verified here: `run_kfold_relation.py` vs `run_lco_eval.py`). We have **withdrawn the margin claim** and are rebuilding a transferable baseline (task A3b) before this axis is written into the thesis. Honest current state: the model reaches 78-82% macro on held-out cameras vs a documented near-floor constant predictor — real but not yet honestly quantified as a margin. With only 2 physical cameras, we additionally concede this is a weak protocol relative to a multi-site deployment claim, and will state that explicitly as a limitation, not a strength.

**Q6: "Scene-only baseline collapsing to 16.9% — engineered to look good?"**
A: No malicious engineering — it's a genuine estimator-definition bug (LCO's scene-only baseline predicts a single constant class per fold, mathematically near-floor for a 4-class problem), not manipulation of scores. We found and disclosed this ourselves before the committee could (brief.md S2, dated 2026-09-06) and withdrew the associated "+60.3pp" claim. This is exactly the kind of self-correction we'd rather present than have discovered live.

**Q7: "Detector 0.79 mAP vs their 0.957 (or 95.7%) — same annotation?"**
A: The "95.7%"/0.957 figure does not exist in the source paper — exhaustive grep of `paper/paper.txt` returns zero hits (independently confirmed here and by a peer audit). The paper's only quantified detector metric is a training-curve read ("mAP ~97% during iterations," L323, nc=4, no test-set protocol). No detector-mAP comparison against the paper is defensible or made. Our own detector (0.791/0.806 mAP50, standalone) was trained on CPU with a forced small epoch/batch budget (Ultralytics-on-MPS convergence bug) — we report this as a training-budget limitation, not a comparison.

**Q8: "Jetson numbers — which model, self-measured?"**
A: Self-measured on real Tegra hardware (TensorRT 10.3.0, verified via platform string in the JSON), not cited. However — and we disclose this — the existing Jetson JSON artifacts (8.62ms/116FPS, 55/64 accuracy, soak, multi-stream, power sweep) belong to pipeline **P1** (round-0/1 ensemble), not the P3 headline pipeline. brief.md's evidence table already labels this correctly ("This is what is on Jetson today," P1 row). README.md's "Thesis Contributions" section does **not** yet carry this same disclosure and should be corrected before submission (see D3).

**Q9: "Three pipelines P1/P2/P3 — isn't that a liability?"**
A: Presented transparently as an evolution, not concealed: P1 (frozen-COCO detector, what's currently deployed on Jetson) → P2 (paper-faithful rewrite, honest but weaker, 50/64 blind) → P3 (entity+relation Transformer, only N>64 evidence in the project, current headline for accuracy claims). The thesis should state upfront which pipeline backs which claim in every figure/table, and we recommend an explicit pipeline-attribution column in every results table (see D).

**Q10: "Val accuracy doesn't predict test (r≈−0.07 to −0.25) — is model selection invalid?"**
A: Correct, and we treat it as a finding, not a flaw to hide: the correlation is negative/non-significant across all measured subsets (N=46: r=−0.247,p=.098; N=22: r=−0.136,p=.545; N=34: r=−0.066,p=.71 — independently confirmed range). Consequence: we do NOT select configs by chasing val→test correlation; we use a **frozen, pre-registered protocol** (blind fusion, one declared test touch) specifically because val cannot be trusted to rank configs at this N. This is exactly what the resolving-power analysis (r5) formalizes.

**Q11: "Prove no data leakage."**
A: Two leakage bugs were found and fixed, disclosed rather than hidden: (1) temperature-scaling calibration originally fit on the TEST set (leaked); honest train-fit ECE=0.114 vs leaked ECE's 0.110/0.101 (`phase0-D3-testfit-leakage-fixes.md`, independently traced here). (2) abstention threshold τ originally selected on TEST; fixed via OOF-selected τ=0.50 (100% coverage, 81.2% acc-on-fired, honest). (3) the LCO camera-grouping leakage (circular KMeans on classifier features) — fixed via classifier-independent grouping (D1). We can walk through each fix with before/after numbers on request.

**Q12: "Practical deployability in a Vietnamese factory?"**
A: Measured (P1, currently deployed): 8.62ms p50 / 116 FPS single-stream, 4-stream zero-drop at 88 FPS aggregate, 36.2-min soak with 0 throttle events at 7.0W of a 15W budget, metadata-only network egress (no raw frames leave device, schema-verified). Caveat honestly: these numbers are for the P1 ensemble on Jetson Orin Nano; P3 (higher-accuracy headline) has not yet been benchmarked on Jetson — re-measurement is scheduled (Lane B, days 2-6). Soak duration (36 min) is a pilot, not a 24/7-readiness claim, and we do not extrapolate it as such.

**Additional dangerous question found — Q13: "Your k-fold significance test for 'model beats scene-only' gives p=0.0375 in one log and p=0.10 in another for what's presented as the same result — which is real?"**
A: Genuinely unresolved before this review; both logs exist (`kfold_relation.log`, Aug16, old token/grouping, p=0.0375 significant; `_zones_eval.log`, Sep5, repaired features, p=0.0697-0.1013 n.s.). The correct answer is to report the **most recent, most methodologically sound** run (repaired scene-grouping, `_zones_eval.log`) as canonical and disclose the earlier number's provenance if asked, rather than let two live artifacts imply the finding is unstable/cherry-picked. This should be resolved (canonical log chosen, older logs archived) before Ch3 is finalized — folding into task A3b's scope is recommended.
