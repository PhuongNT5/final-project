## 3. Blocking bugs/inconsistencies (spot-checked)

**B1 (blocker, likely thesis-document bug).** ch01 line 105 and ch06 lines 227-228 both cite an "8-class joint (~78% top-1)" preliminary result, with ch06 attributing it to "§4.4". Checked: ch04 §4.4 is "Per-Class Breakdown" of the **4-class** headline (Table 4.4), not an 8-class run — no 8-class number appears there. Searched the entire `report/` tree, `sweep_results/relation_tokens/`, and filesystem for anything named `*8class*`/`*joint*`/`*8_class*` (Python venv package matches only) — **found nothing**. Strong suspicion: the "78%" figure is a miscopy/conflation of an unrelated sentence at ch04 line 1113, "**78% of clips collapse onto CarryOverload**" — a class-imbalance statistic, not an accuracy number, and not even about 8 classes. Recommend: either find the real source (check `plans/2026-09-01-unsafenet-r2-rewrite/` for a P2 8-class run — thesis-process-review.md line 50 says P2 "trained on all 8 classes", not checked in depth this session) or strike the "~78% top-1" claim and cite candidate (a) as pure future-work with no preliminary number attached.

**B2 (not a numeric bug, cross-pipeline attribution).** Already flagged by review-edge-deployment (C1/C2): ch05 body presents P1's 56/64 as "the result" in 5+ places while the accuracy-headline pipeline is P3 (54/64 blind) and P3 is not Jetson-deployed. Re-confirmed present as of this session (files still modified per git status, unclear if resolved).

**B3 (spot-checked, no bug found).** ch07 §7.7.1/§7.8.1 k-fold and LCO headline numbers (80.8% top-1/421/516/macro84.2%/NB-CI[76.7,85.0] and 77.7%/401/516/macro81.2%/margin+16.9[12.5,21.2]) match the canonical logs byte-for-byte (`kfold_repeats10_yolo26app_HEADLINE.log`, `lco_seeds5_yolo26L1_CANONICAL.log`) and match brief.md's text. Per-class LCO recalls (70.5/65.7/88.7/100.0) also match across brief.md and ch07. **No inconsistency found in these two headline chains** — they're the best-reconciled numbers in the thesis.

**B4 (structural, already known, reconfirmed).** CarryOverload's 100% recall under every protocol (same-dist, k-fold, LCO) is not a relational-reasoning result — labeling-strategy-review.md §2 shows a 1-line detector-class rule reproduces it exactly (100/100 P/R, train+test). Any macro/aggregate metric that includes CarryOverload is partly measuring this shortcut. Candidate (e)'s 3-class-excl macro is the correct lens but isn't yet in any chapter.

## 4. Top blockers (for final message)

1. **B1** — "8-class ~78% top-1" claim in ch01/ch06 has no findable source; §4.4 cross-ref is wrong (points to 4-class per-class breakdown); likely conflated with an unrelated "78% of clips collapse onto CarryOverload" sentence. Needs resolution before submission — either find the real number (check P2/unsafenet reports) or strike the claim.
2. **C1 (pre-existing, requantified here)** — detector leakage in k-fold/LCO is real and structurally total for the 452 train-partition clips (100% frame_manifest coverage), zero for the 125 test-partition clips. No code exists to run a leakage-free variant; would need a moderate patch to filter the held-out-fold candidate pool. Not attempted (Gate 2 + read-only).
3. **CarryOverload shortcut (B4)** — every "100% recall" and every macro that includes it is contaminated by a trivial detector-class rule, independently confirmed via two routes (class-7-token rule, and zone-all-zero-iff-class-3 in the missing-view-2/7 clips). The already-computed 3-class-excl macro (72.2% mean-of-seeds / 75.0% ensemble, candidate e) is a more honest number and costs nothing to report.
4. **two_proportion_z misuse** (pre-existing, 3 scripts) — still present per git status, unclear if landed.
