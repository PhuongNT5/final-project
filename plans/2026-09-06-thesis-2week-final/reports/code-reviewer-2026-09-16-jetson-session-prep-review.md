## 1. TRTRunner multi-input binding — correct, test has real fidelity
`trt-runner-utils.py` binds every I/O tensor by name in a dict (`self.inputs`/`self.outputs`), fixing the old bug where a second INPUT reassigned `self.host_in/dev_in` and silently dropped the first input's buffer. `run()` binds by kwarg-name (required path for multi-input) or positional-in-declared-order (back-compat). Both `jetson-benchmark.py` and `jetson-multi-stream-pipeline.py` load this exact module via importlib (not a reimplementation) — confirmed via grep, both call `_tru.TRTRunner(...)`.

`tests/test_trt_runner_utils.py` is a genuine regression test, not a reimplementation: it imports the real `trt-runner-utils.py` via `importlib.util.spec_from_file_location`, and its `FakeCuda.memcpy_dtoh_async`/`FakeContext.execute_async_v3` explicitly raise `AssertionError` if a device buffer was never written — this is a real trap for the exact silent-overwrite bug being regressed (an input reassignment would leave one buffer `None`). 2-input fake engine (`tokens`+`mask`) exercises the actual multi-input path; the missing-kwarg and positional-back-compat paths are also covered. This is solid.

Minor: `run()`'s output path returns `outs[self.output_order[0]]` (bare array) when there's exactly one output, else a dict — this differs across P1 (1-output heads, callers use bare-array `.run(x)`) vs P3 relation head (1 output too, so also bare-array despite 2 inputs) — verified this is consistent with how `jetson-measure-latency.py`'s `measure_stage_latency`/`run_parity` consume it (`out = runner.run(**inputs)` then `np.asarray(out)`), fine either way. No bug, just worth knowing the shape-polymorphism exists if a future multi-output engine is added.

## 4. jetson-measure-*.py — fabrication guard audit
Traced every hardware-dependent function in `jetson-measure-latency.py` / `jetson-measure-power.py` / `jetson-full-measurement.py`:
- `run_latency`, `run_parity`, `run_energy`, `run_thermal_soak`, `run_memory`, `run_streams` — each checks `trt is None` (or `dry_run`/missing sources) **before** any numeric field is populated, and returns early with `skipped_reason` + explicit `None`/`{}` for the would-be-real fields. Confirmed no code path computes a numeric result without going through real subprocess/TRT/psutil calls first.
- `TegrastatsSampler` — dry path (`_dry_loop`) only ever appends `{'ts':.., 'dry_run': True}`, no power/temp keys; test (`test_tegrastats_dry_run_never_fabricates_numbers`) asserts `'power_now_mw' not in sample`. Confirmed correct independently.
- `run_energy`'s `else` branch (trt None) still calls `sampler.start()/stop()` and computes `_avg_power_mw` — but since dry-run samples never carry `power_now_mw`, `avg_mw` is `None`, and the `if avg_mw is not None and n:` guard forces `avg_power_w`/`joules_per_inference`/`fps_per_watt` to `None`. Traced by hand — no fabrication, but slightly indirect (relies on `_avg_power_mw` returning `None` for empty list rather than an explicit `dry_run` short-circuit like the other functions use). Not a bug, just less defensive than the peer functions — a future refactor that changes `_avg_power_mw`'s empty-list behavior could reintroduce silent zeros here without an obvious signal.

**Real bug found — schema inconsistency in `run_memory`** (`jetson-measure-power.py:109-122`): the skipped/dry-run branch sets `result['device_free_total_mb'] = None`, but the success branch sets three *different* keys: `device_free_mb`, `device_total_mb`, `device_used_mb`. `device_free_total_mb` is a dead key never produced on the success path, and the null path never sets `device_used_mb`/`device_total_mb` at all. `JETSON-RUNBOOK-2026-09-19.md` Step 9 documents the expected fields as `used_mb`/`total_mb`, confirming the success-path names are the intended contract and the dry-run branch's key is just a typo/copy-paste leftover. Low functional impact (dry-run JSON just has an extra unused null key and is missing the other two null keys) but worth a one-line fix: `device_free_mb = device_total_mb = device_used_mb = None`.

**Runbook/code mismatch**: `JETSON-RUNBOOK-2026-09-19.md` §12 Triage-C tells the operator to cross-check `windows[i].tegrastats.samples[*].temp_c`, but `run_thermal_soak`'s actual schema has a single top-level `result['tegrastats']` (all samples across the whole soak, not nested per-window) and `parse_tegrastats_line` produces a `temps_c` dict (plural, multi-sensor), not a scalar `temp_c`. An operator following the runbook literally on 9/19 will get a `KeyError`/empty-lookup. Low severity (human runbook, not code) but worth a one-line fix before the session since it's dated for 3 days from now.

## 7. General code quality / KISS observations
- Good discipline throughout `benchmark-p3-*.py` and `jetson-measure-*.py`: RNG/random-input generation is consistently hoisted outside timed closures (explicitly commented why, citing measured contamination numbers from an earlier version) — this is exactly the kind of benchmark-methodology rigor that matters for a thesis latency claim.

- `_import_trt()`'s `(None, str(e))` return reuses the second tuple slot for an error string on failure vs a real `cuda` module on success — works (call sites always check `trt is None` first) but the variable name `cuda` holding a string is a minor readability smell; a small dataclass/namedtuple or `(trt, cuda, error)` triple would be clearer for future maintainers, not urgent.

- `jetson-build-trt-engine.py`'s `--model`/`--onnx` addition is minimal and additive; default no-arg path (`targets = [...] if args.model else [P1 MODELS list]`) is unchanged, confirmed by reading the branch — low risk to existing P1 workflow.

## Edge cases scouted (beyond the diff)
- `run_streams` (`jetson-full-measurement.py`) lazily imports `jetson-multi-stream-pipeline.py` only when `not dry_run and source_globs` — on non-Jetson hardware with `--streams` but no `--dry-run`, this would hit an uncaught `ModuleNotFoundError` from `import pycuda.autoinit` inside that module (top-level import, not deferred like `jetson-benchmark.py`'s `import_trt()`). Fails loud rather than silently, so no fabrication risk, just an unhandled-exception UX gap if the runbook is followed off-script. Runbook itself always requires real Jetson for `--streams`, so unlikely to bite on 9/19.
- `run_thermal_soak`'s tight `while time.time() < w_end: runner.run(**fixed_in)` busy-loop has no yield/sleep — fine for a dedicated soak test, but worth knowing it will peg one CPU core plus GPU for the full 30 min (intentional for the thermal test, just noting for anyone reusing this loop elsewhere).
- `_fixed_inputs()` (latency/power) generates one fixed random input per `TRTRunner` instance (`seed=0` in parity, unseeded default in latency) — fine for latency timing (payload content doesn't affect TRT execution time meaningfully) but `run_parity` deliberately reuses the same `fixed_in` across precisions for a fair diff, which is correct and was verified by reading `run_parity`'s loop (input generated once from `ref_runner`, reused for every other precision's `runner.run(**fixed_in)`).
